# Initial Requirements

| ID | Requirement | Acceptance criteria |
|---|---|---|
| REQ-ATLAS-001 | Users can register, locate, search, retrieve, and maintain organization-owned assets. | Valid server and device records support unique identity, status, People location/department/user references, purchase date, optimistic revisions, effective lifecycle history, authorization, audits, REST/OpenAPI and gRPC contracts, memory/PostgreSQL adapter conformance, accessible create/edit/detail/filter workflows, and a provider-neutral DynamoDB seam. |
| REQ-PEOPLE-001 | Assets can be organized by people, shared-use identities, departments, and sites. | Organization-scoped sites, departments, person/shared/public/lab identities, bounded scoped search, multi-user asset relationships, effective-dated assignment history, provider mapping seams, audits, help, and accessible workflows are implemented through provider-neutral contracts. |
| REQ-DIRECTORY-EXPANSION-001 | Sites support structured addresses and a building-and-room hierarchy. | Existing Site API clients remain compatible; buildings and rooms are organization- and site-scoped; addresses validate and persist; location reads enforce directory visibility; memory, PostgreSQL, REST, OpenAPI, gRPC, and accessible UI behavior are tested. |
| REQ-PLATFORM-VALKEY-001 | The runtime provides optional shared Valkey-compatible cache and coordination behavior. | Valkey/Redis-compatible URLs, no-op and memory modes, distributed Guard rate limiting, cache isolation, failure policy, container readiness, Lambda deployment guidance, and architecture traceability are documented and tested without making cache state authoritative. |
| REQ-THREADS-001 | Strategic tags and goals can be attached to records. | Tags and goals have stable IDs and support parent-child relationships. |
| REQ-STORAGE-001 | File storage is abstracted from the application. | Local storage is available now and S3-compatible storage can implement the same interface. |
| REQ-API-001 | REST and gRPC contracts are documented. | OpenAPI and protobuf definitions are checked into the repository. |
| SEC-HTTP-001 | The HTTP service uses secure defaults. | Timeouts, body limits, security headers, and input validation are covered by tests or configuration. |
| A11Y-001 | The interface meets WCAG 2.2 AA at minimum. | Keyboard focus, semantic headings, reduced motion, and accessible status messaging are implemented and tested. |
| DOC-001 | Feature behavior is discoverable. | Branded names always appear with plain-language descriptors and documentation links. |
| DOC-002 | Users can report issues from the application. | The issue destination is configurable and defaults to the public StewardMesh issues page. |
| REQ-FOUNDATION-001 | The platform provides a requirements-driven organization foundation. | Local bootstrap, repository interfaces, adapter seams, shared audit/correlation boundaries, and traceability are defined before feature expansion. |
| REQ-HORIZON-001 | Users can plan useful life, replacement, funding cycles, and forecasts. | Lifecycle assumptions are effective-dated, versioned, auditable, and reportable by fiscal period. |
| REQ-LEDGER-001 | Users can manage procurement, contracts, commitments, budgets, and costs. | Purchase orders, financial statuses, multi-year commitments, actual/estimated/real costs, and budget variance are supported. |
| REQ-STACK-001 | Users can manage software inventory and licensing. | Software, versions, entitlements, assignments, expiration, usage, and PO/contract references are supported. |
| REQ-PATTERNS-001 | Users can define and reuse typed record templates. | Standard and custom templates validate required fields, optional fields, typed references, CSV, API, help, and accessibility behavior. |
| REQ-EXCHANGE-001 | Users can migrate selected records and dependencies safely. | Compressed packages preserve source identity, provenance, checksums, ownership, optional files, idempotency, and holding states. |
| REQ-SIGNALS-001 | Users can configure operational and financial alerts. | Budget, payment, expiration, renewal, license, commitment, and reconciliation rules produce auditable notifications. |
| REQ-REACH-001 | Users can deliver alerts through configurable messaging providers. | SMTP, SES, Gmail, Outlook, Teams-compatible channels, and signed webhooks support testing, retries, and delivery history. |
| SEC-GUARD-001 | Access control protects organization and resource operations. | Local bootstrap, OIDC/OAuth, SAML 2.0 SP-initiated SSO, scoped RBAC, protected built-in roles, accessible custom-role creation from direct permissions and policy bundles, externally sourced ownership locks, explicit local claims, blocked-write enforcement, and audit events are implemented without plaintext credentials or persisted identity assertions. |
| SEC-MCP-001 | MCP access is authenticated, scoped, and auditable. | OAuth 2.1/PKCE, consent, audience validation, confirmation, rate limiting, redaction, and tool restrictions protect MCP operations. |
| REQ-BEACON-001 | Future endpoint clients securely report approved telemetry. | macOS, Windows, and Linux clients support authenticated enrollment, encrypted minimized telemetry, revocation, and updates. |
| REQ-FORGE-001 | Future automation safely deploys clients and machine workflows. | Rollouts, image operations, CI/CD integrations, approvals, least privilege, audit, and rollback are supported. |
