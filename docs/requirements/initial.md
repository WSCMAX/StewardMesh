# Initial Requirements

| ID | Requirement | Acceptance criteria |
|---|---|---|
| REQ-ATLAS-001 | Users can register, locate, search, retrieve, and maintain organization-owned assets. | Valid server and device records support unique identity, status, People location/department/user references, purchase date, optimistic revisions, effective lifecycle history, authorization, audits, REST/OpenAPI and gRPC contracts, memory/PostgreSQL adapter conformance, accessible create/edit/detail/filter workflows, and a provider-neutral DynamoDB seam. |
| REQ-ATLAS-MODELS-001 | Users can define product models and reuse their defaults across repeated asset instances. | Organization-scoped model records support deterministic manufacturer/name/model-number uniqueness, search, view, create, update, retire, import provenance fields, bounded shared specifications, support and warranty/useful-life defaults, model-linked asset counts, asset `modelId` association, immutable applied-default snapshots with source/effective-time provenance, explicit instance overrides, and a model detail that links to matching assets with exact lifecycle/site/department/user/deployment filters and optional grouped counts. Authorization, audits, REST/OpenAPI and gRPC contracts, memory/PostgreSQL adapter conformance, and accessible narrow-width model-to-asset workflows do not silently overwrite instance-specific data. |
| REQ-ATLAS-CATALOG-001 | Users can add configurations, effective prices, and supported replacement paths to reusable Atlas product models. | Organization-scoped configurations attach named or SKU-specific specification overrides to an Atlas model; exact minor-unit list, quote, contract, and estimate prices remain effective-dated and source-typed; directed successor, replacement, and upgrade relationships connect compatible models or configurations without self-links; audits exclude specifications and monetary amounts; and later Atlas and Horizon slices can select stable configurations and price provenance without duplicating Atlas Models or copying catalog ownership into individual assets. |
| REQ-ATLAS-CODES-001 | Users can identify assets through durable barcode and QR associations. | Organization-scoped Code 128 and QR identifiers support multiple active and historical associations, case-preserving normalization, visible provenance, one active primary per asset, conflict-safe replacement and deactivation, optimistic revisions, stable retry behavior, ownership locks, redacted audits, REST/OpenAPI and gRPC contracts, memory/PostgreSQL provider conformance, and accessible manual management. Scanner/device capture and label printing remain separately tracked delivery slices. |
| REQ-PEOPLE-001 | Assets can be organized by people, shared-use identities, departments, and sites. | Organization-scoped sites, departments, person/shared/public/lab identities, bounded scoped search, multi-user asset relationships, effective-dated assignment history, provider mapping seams, audits, help, and accessible workflows are implemented through provider-neutral contracts. |
| REQ-DIRECTORY-EXPANSION-001 | Sites support structured addresses and a building-and-room hierarchy. | Existing Site API clients remain compatible; buildings and rooms are organization- and site-scoped; addresses validate and persist; location reads enforce directory visibility; memory, PostgreSQL, REST, OpenAPI, gRPC, and accessible UI behavior are tested. |
| REQ-PLATFORM-VALKEY-001 | The runtime provides optional shared Valkey-compatible cache and coordination behavior. | Valkey/Redis-compatible URLs, no-op and memory modes, distributed Guard rate limiting, cache isolation, failure policy, container readiness, Lambda deployment guidance, and architecture traceability are documented and tested without making cache state authoritative. |
| REQ-THREADS-001 | Strategic tags and goals can be attached to records. | Organization-scoped tags and goals have stable IDs, unique names, optimistic revisions, cycle-safe parent-child hierarchies, explicit include/suppress rules, visible inheritance provenance, guarded asset and purchase goal links, audited writes, REST/OpenAPI and gRPC contracts, memory/PostgreSQL adapter conformance, and an accessible asset workflow. |
| REQ-STORAGE-001 | File storage is abstracted from the application. | Organization-scoped Vault metadata is audited and separated from bytes; hardened local and S3-compatible adapters share one contract, enforce server-owned keys, size limits, SHA-256 integrity, private access, mandatory S3 encryption, safe fixed endpoints, IAM/workload/assume-role or explicit authentication, and short-lived download authorization without persisting credentials or URLs. |
| REQ-API-001 | REST and gRPC contracts are documented. | OpenAPI and protobuf definitions are checked into the repository. |
| SEC-HTTP-001 | The HTTP service uses secure defaults. | Timeouts, body limits, security headers, and input validation are covered by tests or configuration. |
| A11Y-001 | The interface meets WCAG 2.2 AA at minimum. | Keyboard focus, semantic headings, reduced motion, accessible names and status messaging are implemented and tested; dark/light branding contrast is validated before application, color-vision and non-color warnings are explicit, and critical failures fall back to the verified palette. |
| DOC-001 | Feature behavior is discoverable. | Branded names always appear with plain-language descriptors, contextual examples, accessible help controls, documentation links, and dismissible, skippable, replayable, permission-aware walkthroughs that never gate normal work. |
| DOC-002 | Users can report issues from the application. | The issue destination is configurable and defaults to the public StewardMesh issues page; Guide prefills only sanitized page, component, version, coarse browser, viewport, system, and valid correlation-ID context for review before submission. |
| REQ-WORKSPACE-001 | Authenticated users can move between focused product areas in one coherent, responsive work view. | Persistent product navigation, a current-context header, stable deep links, preserved in-page and multi-step task state, guided person-plus-location selection or authorized inline creation, organization/read-only/scoped/denied permission treatment, recoverable session expiry, Guide integration, semantic landmarks, keyboard focus, and 320-pixel containment are implemented without weakening feature-owned authorization. |
| REQ-FOUNDATION-001 | The platform provides a requirements-driven organization foundation. | Local bootstrap, repository interfaces, adapter seams, shared audit/correlation boundaries, and traceability are defined before feature expansion. |
| REQ-HORIZON-001 | Users can plan useful life, replacement, funding cycles, and forecasts. | Organization-scoped per-asset and per-scenario lifecycle plans support effective-dated immutable versions, optimistic revisions, planned/in-service/refresh-due/approved/retired stages, 1–1200 month useful life, manual or Atlas-purchase-date-derived replacement dates, browser-safe exact minor-unit replacement costs and aggregates through 9,007,199,254,740,991, planning read/write authorization, audits, memory/PostgreSQL provider contracts, REST/OpenAPI and gRPC contracts, deterministic as-of fiscal-year forecasts grouped by department/site/effective tag/direct goal/Atlas asset class, explicit actual/estimated/committed/normalized-real/TCO amounts, mixed-currency rejection, JSON and formula-safe CSV, and accessible authoritative tables with supplemental non-color compact bars. |
| REQ-LEDGER-001 | Users can manage procurement, contracts, commitments, budgets, and costs. | Organization-scoped vendors, multi-asset purchase orders with preserved Vault evidence, independent operational/financial contract states, typed multi-year commitments, integer-minor-unit planned/estimated/actual/billed/paid/committed/normalized-real/TCO costs, idempotent source reconciliation, fiscal-period scenario variance, over-budget state, CSV export, authorization, audit, provider contracts, and accessible workflows are implemented. |
| REQ-STACK-001 | Users can manage software inventory and licensing. | Software, versions, entitlements, assignments, expiration, usage, and PO/contract references are supported. |
| REQ-PATTERNS-001 | Users can define and reuse typed record templates. | Standard and custom templates validate required fields, optional fields, typed references, CSV, API, help, and accessibility behavior. |
| REQ-EXCHANGE-001 | Users can migrate selected records and dependencies safely. | Compressed packages preserve source identity, provenance, checksums, ownership, optional files, idempotency, and holding states. |
| REQ-SIGNALS-001 | Users can configure operational and financial alerts. | Budget, payment, expiration, renewal, license, commitment, and reconciliation rules produce auditable notifications. |
| REQ-REACH-001 | Users can deliver alerts through configurable messaging providers. | SMTP, SES, Gmail, Outlook, Teams-compatible channels, and signed webhooks support testing, retries, and delivery history. |
| SEC-GUARD-001 | Access control protects organization and resource operations. | Local bootstrap, OIDC/OAuth, SAML 2.0 SP-initiated SSO, scoped RBAC, protected built-in roles, accessible custom-role creation from direct permissions and policy bundles, externally sourced ownership locks, explicit local claims, blocked-write enforcement, and audit events are implemented without plaintext credentials or persisted identity assertions. |
| SEC-MCP-001 | MCP access is authenticated, scoped, and auditable. | OAuth 2.1/PKCE, consent, audience validation, confirmation, rate limiting, redaction, and tool restrictions protect MCP operations. |
| REQ-BEACON-001 | Future endpoint clients securely report approved telemetry. | macOS, Windows, and Linux clients support authenticated enrollment, encrypted minimized telemetry, revocation, and updates. |
| REQ-FORGE-001 | Future automation safely deploys clients and machine workflows. | Rollouts, image operations, CI/CD integrations, approvals, least privilege, audit, and rollback are supported. |
